# What JSP Is and the Problem It Solves

--> **JSP (JavaServer Pages)** is a technology for writing dynamic web pages by embedding Java code directly INSIDE an HTML-like document, rather than writing HTML output line-by-line from inside a Java class (which is exactly what raw servlets force you into for anything with substantial markup). A `.jsp` file looks mostly like HTML, with special tags for the dynamic parts.
--> The problem JSP solves is **the awkwardness of generating HTML from pure Java**. Compare:

```java
// Pure servlet approach -- HTML is trapped inside Java string literals,
// escaped, concatenated, and utterly miserable to read/maintain for
// anything beyond a trivial page.
protected void doGet(HttpServletRequest req, HttpServletResponse resp) throws IOException {
    resp.setContentType("text/html");
    PrintWriter out = resp.getWriter();
    out.println("<html><body>");
    out.println("<h1>Products</h1><ul>");
    for (Product p : products) {
        out.println("<li>" + p.getName() + " - $" + p.getPrice() + "</li>");
    }
    out.println("</ul></body></html>");
}
```

```jsp
<%-- JSP approach -- HTML is the primary structure; Java only appears
     where dynamic content is actually needed --%>
<html><body>
<h1>Products</h1>
<ul>
<% for (Product p : products) { %>
    <li><%= p.getName() %> - $<%= p.getPrice() %></li>
<% } %>
</ul>
</body></html>
```

--> **Critical fact: JSP is NOT a separate technology from servlets -- it compiles INTO a servlet.** The very first time a `.jsp` file is requested (or at deployment time, if precompiled), the container's JSP engine translates it into an ordinary `.java` source file implementing `HttpServlet`, compiles that into a `.class` file, loads it, and thereafter serves requests through that generated servlet exactly like any other. Everything you learned about the servlet lifecycle in Theory 01 applies underneath a JSP too -- JSP is best understood as "a more convenient way to author certain kinds of servlets," not a competing technology.

```text
myPage.jsp  --[JSP engine translates]-->  myPage_jsp.java  --[javac compiles]-->  myPage_jsp.class
                                          (extends HttpJspBase / implements HttpJspPage,
                                           which itself extends HttpServlet)
```

# JSP vs Servlets -- When to Use Which

--> This distinction is a very common interview question, and the honest modern answer is nuanced: in a well-architected app you use BOTH, each for what it's naturally good at, following the **MVC pattern** (developed further in Theory 04).

| | Servlets | JSP |
|---|---|---|
| Natural strength | Writing Java logic, control flow, orchestration | Writing HTML/presentation with light dynamic content |
| Awkward at | Generating substantial HTML (string concatenation hell) | Writing complex business logic (Java-in-HTML gets messy fast) |
| Typical role in MVC | **Controller** -- receives the request, invokes business/service logic, decides which view to show | **View** -- renders the data the controller prepared, with minimal logic |
| Compiles to | A servlet, directly, from your `.java` source | A servlet, indirectly, generated by the JSP engine from your `.jsp` source |

--> **The historical arc** -- early JSP-only architectures ("Model 1") put ALL logic directly inside JSP pages using scriptlets, which quickly became an unmaintainable mess of Java and HTML tangled together. The industry converged on **Model 2 (MVC)**: a servlet acts as the controller (handles the request, talks to the service/data layer, puts results into request attributes), then forwards to a JSP that ONLY renders that data, using JSTL and EL (Theory 04) instead of raw Java scriptlets, keeping real logic out of the view entirely. This chapter and Theory 04 build up to that pattern.

# The JSP Lifecycle

--> Because a JSP ultimately becomes a servlet, its lifecycle mirrors the one from Theory 01, with one extra phase up front for translation/compilation.

```text
1. TRANSLATION (first request, or precompiled at build/deploy time)
   JSP engine parses the .jsp file and generates equivalent Java servlet
   source code (implementing HttpJspPage, which extends HttpServlet).
        |
        v
2. COMPILATION
   The generated .java source is compiled into a .class file, exactly
   like any other servlet.
        |
        v
3. INSTANTIATION + jspInit()
   Container instantiates the generated servlet class (once) and calls
   its jspInit() method (the JSP equivalent of a servlet's init()) --
   override with a <%! ... %> declaration if you need custom init logic.
        |
        v
4. _jspService(request, response)
   Called ONCE PER REQUEST -- this is where the translated version of
   your JSP's HTML + scriptlets + expressions actually executes. You
   never write this method yourself -- the JSP engine generates it FOR
   you from the whole body of the .jsp file. (Note: unlike HttpServlet,
   this single method handles ALL HTTP verbs by default -- JSPs aren't
   naturally split into doGet/doPost the way plain servlets are.)
        |
        v
5. jspDestroy()
   Called ONCE, on container shutdown/undeploy -- the JSP equivalent
   of destroy(), for cleanup.
```

--> **Why the first request to a JSP is often noticeably slower** -- unless the container is configured to precompile JSPs at deployment time, translation + compilation happens lazily on the FIRST request for that page, adding real latency to that one unlucky request. Production deployments commonly precompile all JSPs as part of the build/deploy process specifically to avoid this "cold JSP" penalty for real users.

# Scriptlets, Expressions, and Declarations

--> JSP defines several distinct tag syntaxes for embedding Java, each translating into a DIFFERENT part of the generated servlet class -- understanding where each one lands explains their different behavior and scope.

## Scriptlets: `<% ... %>`

--> Raw Java code, copied nearly verbatim into the generated `_jspService()` method body.

```jsp
<%
    int total = 0;
    for (Product p : products) {
        total += p.getPrice();
    }
%>
<p>Total: $<%= total %></p>
```

--> Because it lands inside `_jspService()`, a scriptlet has access to all the JSP **implicit objects** (below: `request`, `response`, `session`, etc.) automatically, exactly as if they were local variables/parameters -- because in the generated code, they actually are.

## Expressions: `<%= ... %>`

--> A Java EXPRESSION (not a full statement -- no semicolon, and it must evaluate to a value) whose result is converted to a `String` and written directly into the response body at that point.

```jsp
<p>Welcome, <%= request.getAttribute("username") %>!</p>
<p>Current time: <%= new java.util.Date() %></p>
```

--> Translates to something like `out.print( request.getAttribute("username") );` inside `_jspService()` -- literally just a shorthand for "compute this value and print it right here."

## Declarations: `<%! ... %>`

--> Declares a MEMBER (field or method) of the generated servlet class itself, OUTSIDE of `_jspService()` -- this is the key difference from a scriptlet, and it has real consequences.

```jsp
<%!
    private int pageHitCount = 0;   // becomes an INSTANCE FIELD of the generated servlet

    private String formatPrice(double price) {   // becomes a METHOD of the generated servlet
        return String.format("$%.2f", price);
    }
%>
<p>This page has been hit <%= ++pageHitCount %> times</p>
<p>Price: <%= formatPrice(19.99) %></p>
```

--> **Gotcha -- declarations create SHARED, mutable instance state**, exactly like an instance field on a hand-written servlet (Theory 01) -- `pageHitCount` above is shared across every concurrent request to this JSP and is NOT thread-safe, for exactly the same reason a raw servlet's instance fields aren't. This is a very easy trap to fall into because declarations look almost identical to scriptlets syntactically (just one extra `!`), but their placement in the generated class is completely different.

```text
<%  ... %>   Scriptlet    --> goes INSIDE _jspService() -- runs per-request, local scope
<%= ... %>   Expression   --> shorthand for out.print(...) inside _jspService()
<%! ... %>   Declaration  --> goes OUTSIDE _jspService() -- becomes a field/method on
                              the whole generated servlet class -- SHARED across requests!
```

# JSP Directives

--> A directive gives the JSP engine instructions about how to translate/process the PAGE ITSELF (as opposed to scriptlets/expressions, which generate runtime behavior). Directives use `<%@ ... %>` syntax and typically appear near the top of the file.

## page Directive

```jsp
<%@ page contentType="text/html;charset=UTF-8" language="java"
         import="java.util.*, com.example.model.Product"
         isErrorPage="false" errorPage="/error.jsp"
         session="true" %>
```

--> Controls page-wide settings: response content type/charset, which Java packages to import (used by scriptlets/expressions in this page), whether this page can act as an error handler for another page (`isErrorPage`) or which page to forward to on an uncaught exception (`errorPage`), and whether a session is auto-created for this page (`session="false"` disables the implicit `session` object entirely, saving overhead for pages that never need one).

## include Directive

```jsp
<%@ include file="header.jsp" %>
```

--> Performs a **static, translation-time** include -- the content of `header.jsp` is textually merged into THIS page's source BEFORE compilation, producing one combined generated servlet. Fast (no runtime overhead per request) but means the including page must be recompiled if the included file changes.

## taglib Directive

```jsp
<%@ taglib prefix="c" uri="jakarta.tags.core" %>
```

--> Declares a tag library this page uses (most commonly JSTL, covered in depth in Theory 04) and binds it to a prefix (`c:` here) used throughout the page.

```text
page directive    --> configures THIS page's translation (imports, content type, error handling)
include directive --> static, compile-time merge of another file's content into this page
taglib directive   --> declares a custom/standard tag library and its prefix for this page
```

--> **Static include (directive) vs dynamic include (the `<jsp:include>` ACTION, distinct from the directive)** -- `<jsp:include page="header.jsp" />` is a RUNTIME include: it invokes the included page as a genuinely separate request-processing step on every request, allowing it to reference a page determined dynamically (e.g. a variable), at the cost of a small per-request overhead the static directive doesn't have. Use the static `<%@ include %>` directive for content that's truly fixed at compile time (a shared header/footer); use the `<jsp:include>` action when the included resource might vary per request or need its own request/response handling.

# Implicit Objects

--> Because a JSP compiles into a servlet, the JSP engine automatically declares a fixed set of variables INSIDE the generated `_jspService()` method -- you can use them directly in scriptlets/expressions without declaring or importing anything, because the generated code already has them in scope.

| Implicit object | Underlying type | What it is |
|---|---|---|
| `request` | `HttpServletRequest` | The current request -- parameters, attributes, headers (same as Theory 02) |
| `response` | `HttpServletResponse` | The current response |
| `session` | `HttpSession` | The current session (unless `<%@ page session="false" %>` disables it) |
| `application` | `ServletContext` | Application-wide shared object, one per deployed web app |
| `out` | `JspWriter` | The output stream used to write to the response body (what `<%= %>` writes to) |
| `config` | `ServletConfig` | This JSP's servlet configuration (init params, etc.) |
| `pageContext` | `PageContext` | Access to all four scopes (page/request/session/application) via one unified API |
| `page` | `Object` (effectively `this`) | The generated servlet instance itself -- rarely used directly |
| `exception` | `Throwable` | Only available on pages marked `isErrorPage="true"` -- the exception that triggered the error forward |

```jsp
<%-- Using several implicit objects together --%>
<p>You are visiting: <%= request.getRequestURI() %></p>
<p>Session ID: <%= session.getId() %></p>
<%
    application.setAttribute("visitCount",
        (Integer) application.getAttribute("visitCount") == null
            ? 1
            : (Integer) application.getAttribute("visitCount") + 1);
%>
<p>Total application visits: <%= application.getAttribute("visitCount") %></p>
```

--> **The four scopes, and how long each one's data lives** -- this table underlies `pageContext`'s unified API and is essential for choosing where to `setAttribute` something:

| Scope | Lifetime | Backing object |
|---|---|---|
| `page` | This one JSP's processing of this one request only -- not even preserved across a `forward` | `pageContext` |
| `request` | One HTTP request, including any internal forwards within it (Theory 02) | `request` |
| `session` | Across many requests from the same client, until timeout/invalidation (Theory 02) | `session` |
| `application` | The entire lifetime of the deployed web application, shared by ALL users | `application` |

# Common Gotchas

--> **Mixing Java and HTML too heavily (Model 1 anti-pattern)** -- scriptlets that contain substantial business logic (database queries, complex conditionals, calling multiple services) make a JSP unreadable and untestable, and mix concerns that should be separated. Theory 04 shows how JSTL + EL eliminate the NEED for scriptlets almost entirely in a well-structured app.
--> **Declarations (`<%! %>`) mistaken for scriptlets** -- as covered above, a single extra `!` moves code from per-request-local to shared-instance-state; a very easy typo/misunderstanding to make with real thread-safety consequences.
--> **Whitespace and JSP comments vs HTML comments** -- `<%-- this is a JSP comment --%>` is stripped entirely during translation and never appears in the output HTML; `<!-- this is an HTML comment -->` IS sent to the browser (and is visible in "View Source"), which matters if you're trying to hide implementation details or Java code fragments from the client.
--> **Uncaught exceptions and error pages** -- an uncaught exception in a JSP, by default, produces the container's generic stack-trace error page (which leaks implementation details -- a real production concern). Set `errorPage="/error.jsp"` on the `page` directive and mark the target page `isErrorPage="true"` to handle this gracefully and access the `exception` implicit object there.

# Best Practices Summary

--> **Understand that JSP IS a servlet under the hood** -- the lifecycle, threading model, and shared-instance-state gotchas from Theory 01 all apply.
--> **Prefer JSTL + EL over scriptlets** for anything beyond the most trivial dynamic content (fully covered in Theory 04) -- keep real logic in servlets/service classes, not JSP scriptlets.
--> **Never put mutable shared state in a `<%! %>` declaration** unless you specifically intend it to be shared across all concurrent requests (rare, and needs synchronization if so).
--> **Use `<%@ page session="false" %>`** for JSPs that genuinely never need a session, to avoid the overhead of creating one needlessly.
--> **Set an `errorPage`** for production JSPs rather than letting uncaught exceptions leak a raw stack trace to users.
--> **Follow Model 2 (MVC)**: servlets as controllers doing logic and orchestration, JSPs as views doing presentation only.
