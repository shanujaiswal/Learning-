### Wireless, Email, WAF, API Security, PKI, and OT/ICS Security

--> Chapter 2 covered firewalls, VPNs, and IDS/IPS at the general network layer; Chapter 3 covered system/application security fundamentals. This chapter fills in six specific, frequently-tested surface areas that sit alongside those: wireless network security, email security (still the single most common initial-access vector alongside phishing from Chapter 4), Web Application Firewalls in depth, API security as its own discipline distinct from general AppSec, PKI/certificate lifecycle management (the trust infrastructure quietly underneath TLS, SAML, and Kerberos alike), and OT/ICS/SCADA security — the physical-world systems where a cyber failure can mean more than data loss.

## Wireless Network Security

--> Wireless networks add an attack surface wired networks don't have: the "network cable" is just radio waves anyone within range can passively receive, so wireless security has always had to work harder specifically on confidentiality and authentication than wired Ethernet historically did.

==> WPA2 vs WPA3
--> WPA2 (Wi-Fi Protected Access 2), the long-standing standard, secures the network in personal ("WPA2-Personal," a single shared pre-shared key/PSK typical of home networks) or enterprise (WPA2-Enterprise, using 802.1X and a RADIUS server to authenticate each user with their OWN credentials rather than one shared password — the wireless-specific application of the centralized-authentication philosophy from Chapters 6/29) modes.
--> WPA2's core weakness: the 4-way handshake (the process two devices use to derive a fresh session key from the shared PSK) can be captured passively, then attacked OFFLINE via a dictionary/brute-force attack against the PSK with zero further interaction with the network — a weak/common Wi-Fi password can be cracked entirely offline once the handshake is captured, and the well-known KRACK (Key Reinstallation Attack) further showed the handshake itself could be manipulated to force nonce/key reuse, undermining the encryption even with a strong password.
--> WPA3 addresses both directly: it replaces the PSK exchange with SAE (Simultaneous Authentication of Equals, based on the Dragonfly key-exchange), which is resistant to offline dictionary attacks — even if an attacker captures the full handshake, they cannot brute-force the password offline, because SAE never exposes enough information in the exchange to attempt that; it also mandates Protected Management Frames (preventing certain deauthentication/spoofing attacks that WPA2 left open) and adds forward secrecy (a compromised password doesn't retroactively let an attacker decrypt PREVIOUSLY captured encrypted traffic, unlike WPA2 where recovering the PSK decrypts every past captured session).
--> WPA3 also adds an Enhanced Open mode for genuinely public/unauthenticated networks (coffee shops, airports) that still encrypts each individual client's traffic uniquely even with no password at all, closing the historical "open Wi-Fi means everyone's traffic is trivially sniffable by anyone else on the same network" gap.

==> Rogue Access Points and Evil Twin Attacks
--> A rogue access point is any unauthorized Wi-Fi access point connected to a network without IT's knowledge or approval — commonly an employee plugging in a cheap personal router for convenience, which can accidentally bridge the secured corporate network to an open, unmonitored wireless network with none of the corporate network's protections.
--> An evil twin attack is more deliberately adversarial: an attacker sets up a rogue AP broadcasting the SAME network name (SSID) as a legitimate network (e.g., "Airport_Free_WiFi" or even a spoofed corporate SSID), often with a stronger signal, so nearby devices connect to the ATTACKER'S access point instead of the real one — from there the attacker can perform a full adversary-in-the-middle position on every connected victim's traffic, including intercepting credentials on any connection that isn't independently encrypted (which is exactly why HTTPS/TLS matters even ON a network you trust, and why a VPN — Chapter 2 — is specifically recommended on any untrusted public Wi-Fi).
--> Detection/defense: Wireless Intrusion Detection Systems (WIDS) specifically watch for duplicate SSIDs broadcasting from unexpected MAC addresses/locations and for anomalous deauthentication-frame floods (a common technique to forcibly disconnect victims from the real AP so they reconnect to the evil twin instead); enterprise deployments also lean on WPA2/WPA3-Enterprise's per-user 802.1X certificate/credential-based authentication specifically because it's much harder for a rogue AP to convincingly impersonate a full enterprise RADIUS backend than to simply clone an open or PSK-based SSID.

## Email Security

--> Email remains one of the most common initial-access vectors precisely because SMTP (the base email protocol) was never designed with sender authenticity in mind — by default, ANY sender can put ANY "From" address they want on an outgoing email, which is the entire technical foundation phishing/spear-phishing/BEC (Chapter 4, and this chapter's IR section) relies on.

==> SPF, DKIM, and DMARC
--> SPF (Sender Policy Framework) — a DNS TXT record published by a domain's owner listing which mail servers are authorized to send email ON BEHALF OF that domain. A receiving mail server checks the connecting server's IP against the sending domain's SPF record; if the sending server ISN'T on that authorized list, the message fails SPF.
```
Example SPF DNS record for acmecorp.com:
  v=spf1 include:_spf.google.com ip4:203.0.113.10 -all

  -- authorizes Google Workspace's mail servers and one specific IP;
     "-all" means STRICTLY reject anything else claiming to be from
     acmecorp.com (a "soft fail" policy would use "~all" instead)
```
--> DKIM (DomainKeys Identified Mail) — the sending mail server cryptographically SIGNS each outgoing message (specific headers plus the body) with a private key, and publishes the corresponding public key in DNS; the receiving server verifies the signature, proving the message genuinely came from that domain's mail infrastructure AND wasn't tampered with in transit — this is the integrity+authenticity half that SPF (which only checks the sending IP, not the message content itself) doesn't cover.
--> DMARC (Domain-based Message Authentication, Reporting and Conformance) — ties SPF and DKIM together into an actual enforceable POLICY, published in DNS, telling receiving mail servers what to DO when a message fails SPF and/or DKIM alignment: `p=none` (just report, take no action — the typical FIRST rollout stage, used to observe what's happening without risking blocking legitimate mail), `p=quarantine` (send failing mail to spam/junk), or `p=reject` (outright refuse delivery). DMARC also enables aggregate reporting back to the domain owner, showing exactly who is sending email claiming to be from their domain — frequently how an organization first discovers someone is actively spoofing them for phishing.
```
Example DMARC DNS record:
  v=DMARC1; p=reject; rua=mailto:dmarc-reports@acmecorp.com; pct=100
```
--> Why all three together, not just one: SPF alone breaks under simple mail forwarding (the forwarding server's IP won't match the original sender's SPF record) and says nothing about content tampering; DKIM alone proves message integrity but doesn't stop an attacker from registering a similar-but-different domain and signing THEIR OWN mail with THEIR OWN valid DKIM key; DMARC is what actually converts "these two technical checks exist" into an enforced, monitored anti-spoofing POLICY tied to the exact visible "From" domain a recipient sees — this is precisely the gap a typosquatted domain like the `micros0ft-login[.]net` phishing example from Chapter 4 exploits, since that's a genuinely different, attacker-owned domain that can pass its OWN SPF/DKIM/DMARC checks perfectly, which is why email authentication protects a domain's OWN name from spoofing but does nothing to stop a convincing look-alike domain — that's a user-awareness and URL-scrutiny problem instead (Chapter 20).

==> Secure Email Gateways (SEGs)
--> A Secure Email Gateway sits inline between the internet and an organization's mail servers, inspecting every inbound (and often outbound) message for phishing indicators, malicious attachments, and malicious links before it ever reaches a user's inbox — going well beyond what SPF/DKIM/DMARC alone provide, since those three only validate SENDER authenticity, not CONTENT safety.
--> Typical SEG capabilities: attachment sandboxing (detonating attachments in an isolated environment, similar in spirit to the Joe Sandbox/any.run tools covered in the Forensics Tooling file, before delivery), URL rewriting/click-time analysis (rewriting every link so that clicking it routes through the SEG's own scanner first, catching malicious pages even if they were CLEAN at the time the email was originally sent but turned malicious later), and impersonation detection (flagging display-name spoofing, like an email showing "CEO Name <random-external-address@gmail.com>" — the visible name is real but the underlying address is not, a very common real-world BEC technique).
--> Common products/categories: Proofpoint, Mimecast, and Microsoft Defender for Office 365 are widely deployed commercial SEGs — nearly all major enterprise email breaches trace back to either a SEG gap (a malicious message that slipped through undetected) or a user bypassing/ignoring a SEG warning banner, making SEG tuning and user training (Chapter 20) genuinely complementary controls rather than either being sufficient alone.

## Web Application Firewall (WAF) — In Depth

--> Chapter 2 introduced the network-layer firewall/IDS-IPS distinction. A WAF operates at a different layer entirely: it inspects Layer 7 (application-layer) HTTP/HTTPS traffic specifically, understanding request structure well enough to recognize malicious PAYLOADS (a SQL injection string, an XSS payload — Chapter 3) that a network firewall, which only understands IPs/ports, is structurally blind to.
--> Rule sets — a WAF's detection logic is organized as rule sets, most commonly built on top of (or directly using) the OWASP ModSecurity Core Rule Set (CRS), a large, community-maintained, continuously updated collection of generic rules detecting broad attack PATTERNS (common SQLi syntax, common XSS payload structures, path traversal sequences) rather than one narrow signature per specific CVE — meaning a well-tuned CRS deployment can catch novel exploitation attempts against a vulnerability it has never specifically seen before, as long as the underlying attack PATTERN resembles known malicious syntax.
--> Virtual patching — a WAF's most operationally valuable capability alongside signature detection: when a specific vulnerability is discovered in a web application (a specific parameter vulnerable to SQLi in a specific endpoint) but a real code fix will take days/weeks to develop, test, and deploy, a WAF rule can be written and deployed in MINUTES to specifically block exploitation attempts against that exact vulnerable parameter/pattern in the meantime — this is precisely the "compensating control" remediation option referenced in Chapter 28's vulnerability management SLA discussion, letting a Critical finding's clock effectively pause on real risk exposure (though not on the underlying SLA/audit clock, which still expects the real fix) while the actual patch is developed.
--> WAF bypass techniques — the reason a WAF is a layer of defense, not a substitute for actually fixing vulnerable code: encoding/obfuscation (URL-encoding, double-encoding, or case-variation of a malicious payload so it no longer matches a rule's literal string pattern while the underlying application still interprets it identically — `SELECT` vs `SeLeCt` vs `%53%45%4C%45%43%54`), HTTP parameter pollution (sending the same parameter multiple times, exploiting inconsistency between how the WAF parses duplicate parameters versus how the backend application actually processes them), and exploiting the request body/content-type parsing gaps (a WAF tuned primarily for standard form/JSON bodies may not fully parse an unusual content-type the backend still happily accepts) — real-world WAF bypass research is an entire sub-field precisely because rule-based pattern matching can always, in principle, be evaded by a sufficiently creative payload encoding, which is why a WAF is correctly understood as raising the bar and buying time (virtual patching), not as a permanent substitute for secure coding practices (Chapter 3) and real remediation.

## API Security

--> Modern applications are increasingly API-first (a web/mobile frontend is often just a thin client calling a backend API directly), which means many of the vulnerabilities historically discussed as generic "web app" flaws now need API-specific framing, formalized by the OWASP API Security Top 10 as its own distinct list from the general OWASP Top 10.
--> Broken Object-Level Authorization (BOLA) — the single most common and highest-impact API vulnerability category: an API endpoint correctly checks that a request is AUTHENTICATED (a valid token/session exists) but fails to check whether THAT SPECIFIC authenticated user is actually AUTHORIZED to access the SPECIFIC object referenced in the request — this is precisely the IDOR concept referenced in Chapter 6's opening paragraph, now named and ranked as its own top API risk category because APIs' object-ID-in-the-URL/payload pattern makes it exceptionally easy to introduce and exceptionally easy to exploit.
```
Legitimate request (user 1001 viewing their own invoice):
  GET /api/v2/invoices/1001

Exploited BOLA (user 1001 simply changes the ID in the request):
  GET /api/v2/invoices/1002

  -- if the API checks only "is this request authenticated" and never
     checks "does the authenticated user 1001 actually OWN invoice
     1002," it happily returns another customer's private invoice.
```
--> The fix is conceptually simple (on every single object-returning endpoint, explicitly verify the authenticated identity owns/is-permitted the specific requested object, not just that SOME valid identity made the request) but is exactly the kind of check that's trivial to individually forget across dozens or hundreds of API endpoints, which is why BOLA remains chronically common despite being well understood — it's a discipline/coverage problem more than a knowledge problem.
--> Rate limiting at the API layer — beyond generic network-layer DDoS protection (Chapter 1/2), APIs need rate limiting scoped to the AUTHENTICATED IDENTITY/API-key/endpoint level, because a single legitimate-looking authenticated client hammering one specific expensive endpoint (a search/export function, a password-reset endpoint enabling a credential-stuffing spray) is a very different, more targeted threat than raw volumetric traffic, and needs limits like "this API key may call this endpoint at most 100 times per minute" rather than a single global request-count threshold. Poorly rate-limited authentication/password-reset endpoints specifically enable credential-stuffing and brute-force attacks even when the rest of an application is otherwise well defended.
--> Excessive Data Exposure — a related, frequent API-specific mistake where a backend endpoint returns a full internal data object (including fields never meant for the client, like internal risk scores or hashed passwords) and RELIES on the frontend to simply not display the extra fields — since an attacker can call the API directly rather than going through the intended frontend, any field returned in the raw API response is effectively exposed regardless of what the official frontend chooses to render, making server-side field filtering (returning only what's genuinely needed) the actual control, not client-side display logic.

## PKI and Certificate Lifecycle Management

--> Chapter 2 mentioned VPN certificates and Chapter 6's SAML/Kerberos sections both rely on signed, verifiable trust — PKI (Public Key Infrastructure) is the underlying system that makes "here is a signature, and here is proof of WHO signed it" actually verifiable at scale, via a hierarchy of trust anchored in Certificate Authorities (CAs).
--> Core chain of trust: a Root CA's certificate is trusted implicitly (pre-installed in operating systems/browsers); the Root CA signs Intermediate CA certificates; an Intermediate CA signs the actual end-entity (leaf) certificates websites/servers/users present — this multi-tier structure lets the highly sensitive Root CA key stay offline and rarely used, while Intermediate CAs handle day-to-day issuance, so a compromised Intermediate can be revoked without having to revoke trust in the Root itself.
```
Root CA (offline, maximally protected)
   |
   +-- Intermediate CA (issues day-to-day certs)
          |
          +-- Leaf/end-entity certificate: acmecorp.com
              (what a browser actually receives during a TLS handshake)
```
--> Certificate lifecycle stages: Request (a server/organization generates a key pair and a Certificate Signing Request, CSR, containing its public key and identity details), Validation (the CA verifies the requester actually controls the domain/organization — Domain Validation checks basic domain control, Organization/Extended Validation additionally verifies real-world business identity), Issuance (the CA signs and issues the certificate), Deployment, Renewal (certificates are deliberately short-lived — modern public TLS certs commonly last around 90 days specifically to limit how long a compromised or mis-issued certificate stays dangerously valid, which has driven widespread automation like ACME/Let's Encrypt to handle frequent renewal without manual admin work), and Revocation (if a private key is compromised or a cert was mis-issued, the CA publishes it as revoked via CRLs — Certificate Revocation Lists — or the faster, real-time OCSP — Online Certificate Status Protocol — check, so relying parties can reject a certificate even before its normal expiry date).
--> Why lifecycle MANAGEMENT (not just issuance) is its own operational discipline: an expired certificate on a production service is one of the most common, entirely self-inflicted causes of a sudden outage (browsers/clients outright refuse to connect, correctly treating an expired cert as untrustworthy) — large organizations run dedicated certificate-inventory/expiry-monitoring tooling specifically to avoid this, because manually tracking hundreds/thousands of certificates' individual expiry dates across an enterprise reliably fails at scale, the exact same "you can't manage what you don't inventory" lesson from Chapter 28's asset discovery section, applied to certificates specifically.

## OT/ICS/SCADA Security

--> Operational Technology (OT) covers the systems that monitor and control physical processes — Industrial Control Systems (ICS) broadly, with SCADA (Supervisory Control and Data Acquisition) as a common specific architecture used across power grids, water treatment, and manufacturing, and PLCs (Programmable Logic Controllers) as the actual field-level devices that read sensors and drive physical actuators (valves, motors, switches).
--> The core reason OT security is treated as its own discipline rather than "IT security applied to factories": OT's priority ordering is inverted from typical IT security. IT security's usual priority is broadly Confidentiality > Integrity > Availability; OT overwhelmingly prioritizes Availability and Safety first — an ICS controlling a chemical plant's pressure valves genuinely cannot be taken offline for an emergency patch the way a web server can, because the physical process it's controlling doesn't pause just because IT wants to apply a security update, and a poorly-timed reboot or an aggressive vulnerability SCAN (Chapter 28) that would be routine against an IT server can itself crash a fragile, decades-old PLC and halt or endanger a physical process.
--> OT systems are also frequently far OLDER and less patchable than typical IT infrastructure — many industrial control systems run for 15-20+ years on legacy, sometimes unsupported operating systems, because the surrounding physical machinery they control has an equally long service life and replacing the control system means an extremely costly, carefully-scheduled physical plant shutdown, not a routine software update — meaning the realistic defensive strategy is very often network segmentation/isolation of OT from IT networks (an OT-specific application of the segmentation principles from Chapter 2/Zero Trust content) and heavy monitoring, rather than the constant patch-cycle approach that works for IT (Chapter 3).
--> The Mirai botnet (already introduced in Chapter 4 as a classic IoT botnet example) is directly relevant here as a cautionary bridge between consumer IoT and OT/ICS risk: Mirai compromised huge numbers of IoT devices (cameras, routers) purely through default/weak credentials, with zero sophisticated exploitation required — the exact same "insecure-by-default embedded device with weak/default credentials, rarely patched, rarely monitored" profile applies just as directly to a great deal of real-world industrial/OT equipment, which is precisely why OT environments are considered a uniquely attractive, historically under-defended target, and why real, publicly documented ICS-targeting incidents (attacks against power-grid control systems, water treatment systems) have specifically exploited exposed, weakly-authenticated, unpatched OT devices reachable directly from the internet or from an inadequately segmented IT network.
--> Practical OT security priorities, in the order they're actually approached in the field: (1) network segmentation between IT and OT (often formalized via the Purdue Model, a reference architecture layering OT into distinct zones from field-level devices up through enterprise IT, with tightly controlled, monitored crossing points between layers), (2) asset inventory of OT devices specifically (many organizations genuinely don't have a full, accurate inventory of every PLC/sensor on their OT network — Chapter 28's discovery problem again, but harder, since many OT devices can't run a standard scanning/monitoring agent at all), (3) monitoring for anomalous OT network traffic rather than relying on patching as the primary defense, and only then (4) a carefully scheduled, safety-reviewed patching program for whatever OT components can actually tolerate it.

## Tying It Together

--> Wireless security's core arc is WPA2's offline-crackable handshake giving way to WPA3's SAE-based resistance to that exact attack class, with rogue APs/evil twins remaining a social-plus-technical threat that per-user enterprise authentication (802.1X) and WIDS monitoring specifically target.
--> SPF, DKIM, and DMARC together authenticate that an email genuinely came from the domain it claims to, closing the "anyone can fake the From address" gap SMTP left open by design — but only for THAT domain's own name, which is why look-alike/typosquatted domains (Chapter 4) still require human awareness and SEG-level content inspection, not just DNS-level authentication.
--> A WAF adds application-layer (Layer 7) inspection network firewalls structurally can't provide, with virtual patching as its single most operationally valuable capability and encoding/parameter-pollution-based bypasses as the permanent reminder that a WAF buys time, not a substitute for fixing the underlying code.
--> API security reframes familiar AppSec problems at API scale — BOLA is IDOR renamed and ranked as the top API risk, and rate limiting/data exposure controls need to be scoped to identity/endpoint granularity rather than generic network-level thresholds.
--> PKI's CA hierarchy and certificate lifecycle (issue -> validate -> deploy -> renew -> revoke) is the quiet trust infrastructure underneath TLS, SAML, and (in its own tickets-not-certificates way) Kerberos alike, and lifecycle MANAGEMENT — catching renewals before expiry — is where real-world outages, not exotic attacks, most often actually happen.
--> OT/ICS/SCADA security inverts IT's usual CIA priority toward Availability-and-Safety-first, runs on far less patchable legacy equipment, and — as Mirai's IoT-botnet pattern of default-credential, unmonitored, internet-reachable devices makes clear — segmentation and monitoring, not the patch cadence that works for ordinary IT, are the realistic first line of defense.
