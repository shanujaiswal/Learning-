# Infrastructure as Code (IaC)

--> Infrastructure as Code means defining cloud infrastructure (VMs, networks, storage buckets, IAM permissions, firewall rules) as version-controlled configuration files, rather than clicking through a cloud provider's web console by hand -- the same infrastructure can then be recreated identically (in a new region, a disaster-recovery environment, or a fresh account) just by re-applying the same files.
--> **Terraform** (HashiCorp) -- the most widely used IaC tool, cloud-provider-agnostic (the same tool/language, HCL, can define AWS, Azure, and GCP resources, unlike provider-specific tools). Infrastructure is described in `.tf` files; `terraform plan` shows exactly what would change before anything is actually applied, and `terraform apply` executes it.
```hcl
resource "aws_s3_bucket" "example" {
  bucket = "my-app-data-bucket"
  # a missing / misconfigured "acl" or bucket-policy block here is exactly
  # the class of mistake covered in the S3 misconfiguration section below --
  # IaC makes infrastructure repeatable, but a flawed template now
  # reproduces the SAME misconfiguration everywhere it's applied
}
```
--> **AWS CloudFormation** -- AWS's own native, AWS-only equivalent to Terraform (JSON/YAML templates instead of HCL) -- functionally similar in purpose, just locked to a single cloud provider rather than being multi-cloud.
--> Security relevance of IaC specifically: it turns infrastructure misconfiguration into a CODE-REVIEW problem rather than a one-off human mistake -- a bad security-group rule or an over-permissive IAM policy written into a Terraform file gets reproduced identically every time that file is applied, and conversely, a properly reviewed/scanned IaC template (using a tool like `tfsec` or `checkov` to statically scan for insecure configurations before deployment) prevents that class of mistake from reaching production at all. This connects directly to the DevSecOps/CI-CD Security content already covered in this track -- IaC scanning is typically one of the automated gates in that same pipeline, alongside SAST/dependency scanning.
--> From an attacker/pentester's perspective (connecting to the Cloud Penetration Testing content in the Ethical Hacking track), a leaked or improperly-secured IaC repository is itself a high-value target -- Terraform state files in particular can contain sensitive values (database passwords, API keys) in plaintext by default unless remote state encryption is configured, making a leaked `.tfstate` file roughly equivalent to a leaked secrets dump.

# Serverless Security Considerations

--> The Cloud Skills roadmap area introduces serverless (AWS Lambda, Azure Functions, GCP Cloud Functions) as a deployment model where you provide only the function code, and the cloud provider handles provisioning, scaling, and patching the underlying servers entirely.
--> Removing server management doesn't remove security responsibility -- it shifts WHERE the risk concentrates. The most common real-world serverless security issues: over-permissive IAM roles attached to a function (a Lambda function granted far broader permissions "just in case" than the one specific action it actually performs, so a vulnerability IN that function's code becomes a much bigger blast radius than intended); injection vulnerabilities in the function's own code (a serverless function is still just application code, and is just as vulnerable to the injection/input-validation issues covered in the OWASP Top 10 content if it isn't written carefully); and insecure use of environment variables for secrets (storing an API key or database password directly as a plaintext environment variable rather than pulling it from a dedicated secrets manager at runtime).
--> The Principle of Least Privilege (already covered elsewhere in this track) applies especially sharply to serverless IAM roles specifically because functions are so granular and numerous -- a well-run serverless environment has dozens or hundreds of small, tightly-scoped roles (one per function, permissioned to exactly what that function needs) rather than a handful of broad roles shared across many functions.

# GCP -- Google Cloud Platform Fundamentals

--> This track's Cloud Security file already covers AWS and Azure in depth -- GCP is the third major cloud provider and uses a somewhat different organizational/terminology model worth knowing at a basic level.
--> **Project** -- GCP's core organizational unit (roughly analogous to an AWS account or an Azure subscription) -- billing, IAM permissions, and most resources are scoped to a specific project, and larger organizations group many projects under an "Organization" and intermediate "Folders" for hierarchical policy management.
--> **IAM in GCP** -- built around binding a "member" (a user, service account, or group) to a "role" (a set of permissions) on a specific "resource" (a project, or an individual resource within it) -- conceptually similar to AWS IAM policies, but GCP's role-hierarchy model is more explicitly hierarchical by default (permissions granted at the Organization or Folder level automatically cascade down to every Project beneath it, unless explicitly restricted).
--> **Core compute/storage services** -- Compute Engine (VMs, analogous to AWS EC2), Cloud Storage (object storage, analogous to S3 -- covered in more depth below), Cloud Functions (serverless, analogous to Lambda), GKE / Google Kubernetes Engine (managed Kubernetes, the platform GCP itself pioneered Kubernetes on top of).
--> **Service accounts** -- GCP's mechanism for granting an application or VM its own identity/permissions (analogous to an AWS IAM role attached to an EC2 instance) -- a service account key file downloaded and left in a public code repository or an exposed storage bucket is one of the most common real-world GCP compromise vectors, directly paralleling the AWS access-key-leak scenarios already discussed in this track's cloud content.
--> Attacker/defender takeaway: despite the different naming (Projects vs Accounts, Cloud Storage vs S3, GKE vs EKS), the SAME fundamental misconfiguration classes recur across every cloud provider -- over-permissive identity/service-account permissions, publicly-exposed storage, and unrotated/leaked long-lived credentials. Learning one cloud provider's security model deeply transfers most of its value to the others.

# Cloud Storage Providers as Attack Surface

--> Beyond the enterprise cloud PLATFORMS (AWS/Azure/GCP) already covered, everyday cloud STORAGE services are a distinct and very common attack surface/data-exposure vector worth naming explicitly.
--> **Amazon S3 (Simple Storage Service)** -- AWS's object storage service, and the single most common source of large-scale accidental data breaches in the cloud era -- a "bucket" left with public read (or worse, public write/list) access exposes every file inside it to anyone who discovers or guesses the bucket name, with no further exploitation needed at all. Automated bucket-name-guessing/scanning is a standard recon technique specifically because misconfigured-but-still-common bucket naming patterns (`companyname-backups`, `companyname-prod-data`) make guessing surprisingly effective; tools built for exactly this (e.g. checking a list of candidate bucket names for public accessibility) are a standard part of external recon in a cloud-focused engagement, connecting directly to the Cloud Penetration Testing content in the Ethical Hacking track.
--> **Dropbox, Google Drive, OneDrive, Box, iCloud** -- consumer/business file-sync-and-share services, which introduce a different but related risk profile: rather than a single infrastructure misconfiguration exposing everything at once (the S3 pattern), the risk here is typically per-FILE oversharing -- an employee generating a "anyone with the link can view" share link for a sensitive document, which can then be discovered, forwarded, or indexed far more widely than intended. This is also a well-documented technique on the OFFENSIVE side -- blending malicious payload delivery or C2 (command-and-control) traffic through a legitimate, widely-allowed cloud-storage domain (since many organizations' egress filtering allowlists Dropbox/Google/Microsoft domains by default) makes malicious traffic far harder to distinguish from ordinary business use, a living-off-the-land-style technique conceptually related to the LOLBAS/GTFOBins content covered in the Ethical Hacking track.
--> The defensive throughline across both patterns: cloud storage (whether an S3 bucket or a Google Drive share link) needs the SAME "who can actually access this, and did we mean for them to" review as any other access-control surface -- the Cloud Security content's emphasis on least-privilege IAM applies just as directly to a storage bucket's access policy or a share link's permission scope as it does to a compute instance's role.
