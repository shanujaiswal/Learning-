# Disk and Memory Forensics Tools

--> The Digital Forensics Fundamentals file already introduces FTK Imager for disk/memory acquisition -- this section names the remaining tools commonly referenced in IR/forensics toolkits and CTF forensics challenges.
--> **WinHex** -- a low-level hex editor and disk-analysis tool for Windows, used to inspect raw disk sectors, recover deleted files by manually locating file signatures/headers ("file carving") when filesystem metadata is gone, and examine raw binary data byte-by-byte. It's a manual, granular complement to higher-level forensics suites -- useful exactly when an automated tool's parser doesn't understand a corrupted or unusual filesystem/file format and a human needs to read the raw bytes directly.
--> **memdump** -- a small, focused Linux/Unix utility that dumps the full contents of physical RAM to a file for offline analysis, without requiring the more complex setup of some other memory-acquisition tools -- the resulting image is then typically analyzed with a tool like Volatility (which parses OS-specific memory structures to recover running processes, network connections, and injected code that only ever existed in memory, never touching disk).
--> **Autopsy** -- a free, open-source graphical digital forensics platform (built on top of The Sleuth Kit) that ties disk-image analysis together into one interface: file recovery/carving, timeline analysis (reconstructing a chronological sequence of file creation/access/modification events across an entire disk image), keyword searching across all recovered files, and web-history/registry parsing. It's the closest open-source equivalent to a commercial suite like EnCase or FTK's full product (FTK Imager, already covered, is just FTK's free acquisition-only component).
--> The common thread across all of these: disk/memory forensics tooling exists on a spectrum from fully automated/high-level (Autopsy parsing a whole disk image and building a timeline for you) down to fully manual/low-level (WinHex letting you read raw bytes when nothing else can make sense of the data) -- a real investigation typically starts with the automated tools and drops down to manual analysis only for the specific artifacts that need it.

# Network Testing Tool -- hping

--> **hping3** -- a command-line tool for crafting and sending custom TCP/UDP/ICMP packets with fine-grained control over nearly every header field (flags, source port, TTL, fragmentation), going well beyond what standard `ping` (ICMP-only, fixed format) can do.
--> Common uses directly relevant to this track: firewall/ACL rule testing (sending a crafted packet with specific flags to see whether a firewall permits or blocks it, without needing a full application to generate that traffic), manual TCP SYN-scanning of a single port when a full nmap scan isn't warranted, and basic network-latency/throughput testing between two points using a specific protocol/port rather than generic ICMP.
```bash
hping3 -S -p 443 target_ip          # send a single crafted TCP SYN packet to port 443 - manual equivalent of an nmap SYN scan against one port
hping3 --icmp target_ip             # ICMP mode, similar to ping but with hping's additional flag/header control
hping3 -S -p 80 --flood target_ip   # flood mode - sends packets as fast as possible; ONLY ever used in an authorized load/resilience test on infrastructure you own, given the DoS-adjacent nature of a flood
```
--> hping's value over nmap for this specific use case is precision -- nmap is built for scanning many ports/hosts efficiently, while hping is built for constructing and inspecting the response to ONE very specific, hand-crafted packet, which is exactly what firewall-rule verification or manual protocol-behavior testing calls for.

# Malware and URL Sandboxes -- Beyond VirusTotal

--> The Ethical Hacking reconnaissance note already covers VirusTotal (multi-engine static/hash-based file and URL scanning) and WHOIS -- this section covers the DYNAMIC analysis sandboxes and URL-specific tools that complement it.
--> **Joe Sandbox** -- a dynamic malware analysis sandbox: rather than just checking a file's hash/signature against antivirus engines (VirusTotal's core model), it actually EXECUTES the suspicious file in an isolated, instrumented virtual environment and records its full runtime behavior -- network connections made, files/registry keys created or modified, processes spawned -- producing a detailed behavioral report even for malware that's brand new and unrecognized by any AV signature.
--> **any.run** -- an interactive dynamic sandbox with the same core idea as Joe Sandbox (detonate the sample, observe behavior), but with a distinguishing feature: the analyst gets a live, interactive VM session to click through prompts, wait out a delay, or take actions the malware might be waiting for before it triggers its real payload -- some malware deliberately stalls or checks for signs of automated sandboxing (no mouse movement, VM-specific artifacts) before running, and an interactive session can defeat those evasion checks.
--> **urlscan.io** -- submits a URL and returns a full scan: a screenshot of the resulting page, every network request/resource it loaded, the DOM/JavaScript content, and metadata about the hosting infrastructure -- useful for safely previewing a suspicious link (from a phishing email, for instance) without visiting it directly in a real browser, and for building a picture of a phishing kit's full infrastructure (what domains/CDNs it touches) rather than just the one link that was reported.
--> **urlvoid** -- aggregates reputation checks for a given domain/URL across multiple blocklist and reputation-scoring engines simultaneously (conceptually similar to how VirusTotal aggregates multiple AV engines for a file), giving a quick "how many services flag this as suspicious" signal as a fast triage step before deeper analysis.
--> When to use which: VirusTotal/urlvoid for a fast reputation/signature check ("has anyone already flagged this"); Joe Sandbox/any.run when you need to actually understand NEW, unrecognized malware's real-world behavior; urlscan.io specifically for URL/web-based threats where the page's visual appearance and loaded resources matter.

# DNS Sinkholes

--> A DNS sinkhole is a DNS server configured to return a FALSE (controlled) IP address for domains known or suspected to be malicious -- instead of resolving to the attacker's real command-and-control server, an infected machine's DNS query for that domain gets redirected to an internal server the defenders control (or simply to a non-routable address, killing the connection attempt entirely).
--> This serves two purposes at once: it PREVENTS the malware from ever reaching its actual C2 infrastructure (since the connection is never established to the real, malicious IP), and it gives defenders a high-confidence DETECTION signal -- any internal host that queries a known-malicious domain and gets redirected to the sinkhole has, by definition, some form of compromise or malicious software present, which is a far more actionable alert than most generic IDS signatures produce.
--> Sinkholing connects directly to the threat intelligence content covered elsewhere in this track -- a sinkhole is only as good as the malicious-domain feed/indicator list feeding it, which is exactly the kind of curated threat-intel data (from ATT&CK-mapped campaign research, commercial feeds, or internal incident findings) discussed in the Cyber Threat Intelligence file.

# Jump Servers / Bastion Hosts -- A Deeper Look

--> A jump server (also called a bastion host) is a single, heavily hardened and closely monitored server that acts as the SOLE entry point for administrative access into a sensitive network segment -- rather than allowing direct SSH/RDP from the general corporate network (or the internet) straight to production servers, admins first connect to the jump server, and only FROM there connect onward to the actual target systems.
--> This achieves several things at once: it collapses "which machines can reach production admin interfaces" down to one small, well-monitored chokepoint (rather than every admin's individual laptop being a potential entry vector); it enables detailed session logging/recording at a single point (many jump-server setups record every keystroke/command of every administrative session passing through, which is invaluable during a later incident investigation); and it lets the sensitive network segment itself have much stricter inbound firewall rules (only accepting connections FROM the jump server's specific IP, from nowhere else).
--> Connects directly to the Zero Trust and network-segmentation content already covered in this track -- a jump server is one of the most concrete, practical implementations of "never trust, always verify, minimize standing access" in an otherwise traditional (non-Zero-Trust-native) network architecture, and is frequently one of the first things a penetration tester specifically looks to identify and, if possible, compromise, since it represents such a concentrated point of privileged access.

# HIPS vs NIPS vs NIDS -- Precise IDS/IPS Terminology

--> This track's Network Security file already covers IDS/IPS generically (detecting vs actively blocking malicious traffic) -- this section names the specific deployment-location variants of that same concept, since certification material and vendor documentation frequently use these precise acronyms rather than the generic terms.
--> **NIDS (Network Intrusion Detection System)** -- monitors network traffic (typically via a mirrored/SPAN port or network tap so it sees a copy of traffic without sitting inline) and ALERTS on suspicious patterns, but does not itself block anything -- a human or downstream system has to act on the alert.
--> **NIPS (Network Intrusion Prevention System)** -- the same network-level monitoring, but deployed INLINE (directly in the traffic path) so it can actively drop/block malicious traffic in real time, not just alert on it. The trade-off: an inline NIPS is a potential single point of failure/latency for all traffic passing through it, whereas a NIDS (out-of-band) can never itself take down network traffic even if it misbehaves.
--> **HIPS (Host Intrusion Prevention System)** -- the same prevention concept, but running as an agent on an individual ENDPOINT rather than watching network traffic -- monitoring/blocking suspicious process behavior, file modifications, or system-call patterns on that specific machine. This overlaps significantly with, and in modern products is often bundled directly into, EDR tooling (covered in this track's Endpoint Security file) -- "HIPS" as a standalone product category has largely been absorbed into broader EDR platforms, but the term still appears frequently in certification material and older documentation.
--> The pattern across all three: NIDS/NIPS share the network-vs-host distinction that ALSO applies to firewalls (network firewall vs host-based firewall, already covered in this track) -- network-level tools protect everything on a given network segment at once but can't see inside encrypted traffic or host-internal activity, while host-level tools (HIPS, host firewalls, EDR) see exactly what's happening on one machine but need to be deployed/maintained on every endpoint individually.
