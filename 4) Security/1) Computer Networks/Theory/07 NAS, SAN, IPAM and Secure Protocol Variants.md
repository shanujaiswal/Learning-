# NAS vs SAN -- Network-Attached vs Storage-Area Storage

--> **NAS (Network-Attached Storage)** -- a storage device that connects directly to a regular network (Ethernet/IP) and presents storage as FILES, over file-sharing protocols like SMB/CIFS (Windows) or NFS (Linux). To a client machine it looks like a shared folder/network drive -- simple to set up, but every request travels over the same general-purpose network as everything else.
--> **SAN (Storage Area Network)** -- a dedicated, separate network (often Fibre Channel, sometimes iSCSI over Ethernet) connecting servers to shared BLOCK-level storage. To a server, a SAN volume looks like a local raw disk, not a shared folder -- the server's own filesystem is built on top of it. This is what large databases and virtualization hosts (ESXi clusters, covered below) typically use, since block-level access is faster and lower-latency than file-level access.
--> The practical distinction to remember: NAS shares FILES over a normal network; a SAN presents raw BLOCK storage over its own dedicated network. NAS is simpler/cheaper to deploy; SAN scales better for performance-sensitive, mission-critical workloads.
--> Security angle: a NAS box exposed with weak/default credentials or an open SMB share is a common ransomware target and a frequent easy win in internal penetration tests -- misconfigured NAS shares showing up as anonymously-readable/writable is a classic enumeration finding (`smbclient -L //target -N` covered in the Ethical Hacking enumeration file). A SAN, since it's usually isolated on its own dedicated fabric/VLAN, has a smaller direct attack surface but a correspondingly bigger blast radius if that isolation is ever bridged (e.g. a misconfigured iSCSI target reachable from a general VLAN).

# IPAM -- IP Address Management

--> IPAM (IP Address Management) is the practice/tooling for tracking and administering an organization's IP address space -- which subnets exist, which addresses are assigned (statically or via DHCP), which are free, and associated DNS records -- across an increasingly large and dynamic network (cloud VPCs, VLANs, VPNs, containers all consuming addresses).
--> Without IPAM, address management is done ad hoc (a spreadsheet, or just "whatever the next free IP looks like") -- this breaks down fast once a network has more than a handful of subnets, leading to IP conflicts, forgotten/orphaned DNS records, and no clear audit trail of what's actually plugged into the network at a given time.
--> IPAM tooling typically integrates directly with DHCP and DNS (sometimes described together as "DDI" -- DNS/DHCP/IPAM) -- when DHCP hands out a lease, the IPAM system automatically records which device/MAC got which address and for how long, and can auto-create/retire the matching DNS record.
--> Security relevance: IPAM data is valuable during incident response -- "what device had IP 10.0.4.87 at 14:32 UTC on the day of the breach" is exactly the kind of question an IPAM system (or DHCP lease logs, at minimum) needs to answer quickly, connecting directly to the log-analysis content in the Cyber Security track.

# Named Virtualization Platforms

--> The Operating Systems track covers the CONCEPT of virtualization (hypervisor, VM, guest OS, host OS) -- this section names the actual products you'll encounter in real environments and CTF/lab setups.
--> **VMware** -- the dominant enterprise virtualization vendor. **VMware ESXi** is a Type 1 (bare-metal) hypervisor -- it runs directly on server hardware with no underlying host OS, used to run many production VMs on a single physical server in a datacenter. **VMware Workstation/Fusion** are Type 2 (hosted) hypervisors -- they run as an application on top of an existing OS (Windows/macOS), which is what most people use to spin up practice/lab VMs on their own laptop.
--> **VirtualBox** -- a free, cross-platform Type 2 hypervisor from Oracle, extremely common for home labs, TryHackMe/HackTheBox practice VMs, and running Kali/ParrotOS/Metasploitable VMs alongside a normal host OS.
--> **Proxmox VE** -- a free, open-source Type 1 hypervisor platform (built on KVM/Linux) with a web-based management UI, popular as a self-hosted alternative to VMware ESXi for home labs and smaller organizations that want enterprise-style VM/cluster management without commercial licensing costs.
--> Type 1 vs Type 2 matters for security posture: a Type 1 hypervisor (ESXi, Proxmox/KVM) has a smaller, more hardened attack surface since there's no general-purpose host OS underneath it to compromise -- but a vulnerability IN the hypervisor itself (a "VM escape") is correspondingly more severe, since it sits directly between every guest VM and the physical hardware.

# Secure Protocol Variants -- DNSSEC, LDAPS, SRTP, S/MIME

--> These four are the "secure version of X" protocols that come up alongside the more commonly covered FTP-vs-SFTP and SSL-vs-TLS comparisons already in this track -- each adds authentication/encryption to a legacy protocol that originally had none.
--> **DNSSEC (DNS Security Extensions)** -- adds cryptographic SIGNATURES to DNS records, so a resolver can verify a DNS response actually came from the legitimate zone owner and wasn't tampered with in transit. Plain DNS has no integrity check at all, which is exactly what makes DNS poisoning/cache poisoning (covered elsewhere in this track) possible -- DNSSEC doesn't encrypt DNS traffic (that's a separate concern, addressed by DNS-over-HTTPS/TLS), it just proves the answer wasn't forged.
--> **LDAPS (LDAP over SSL/TLS)** -- plain LDAP (used for directory lookups against Active Directory, covered in the Ethical Hacking enumeration and AD-attacks files) transmits queries -- including bind/authentication credentials in some configurations -- in cleartext by default. LDAPS wraps the same LDAP protocol inside a TLS tunnel (traditionally port 636, vs 389 for plain LDAP), so credentials and directory data aren't sniffable on the wire.
--> **SRTP (Secure Real-time Transport Protocol)** -- encrypts and authenticates the actual voice/video media stream in VoIP and video-conferencing calls (RTP is the underlying unencrypted transport). Without SRTP, a MITM position on the network can eavesdrop on or inject into a live call's audio/video stream directly.
--> **S/MIME (Secure/Multipurpose Internet Mail Extensions)** -- adds digital signatures and encryption to email messages using the sender/recipient's own PKI certificates (connecting directly to the PKI and digital signatures content in the Cryptography track). A signed email proves the message wasn't altered and genuinely came from the claimed sender; an encrypted one keeps the body unreadable to anyone except the intended recipient, even if the mail server itself is compromised or the message is intercepted in transit -- this is a meaningfully stronger guarantee than just relying on SMTP-over-TLS, which only protects the message hop-to-hop between mail servers, not end-to-end.

# Wireless Encryption Standards -- WEP vs WPA vs WPA2 vs WPA3, WPS, EAP vs PEAP

--> This track's Wireless Networking Fundamentals file and the Ethical Hacking track's Wireless Network Security file cover WPA2 and general wireless attack surface in depth -- this section fills in the full standards lineage and the enterprise authentication pieces (EAP/PEAP) for completeness.
--> **WEP (Wired Equivalent Privacy)** -- the original, now completely broken Wi-Fi encryption standard. Its RC4-based implementation and small, reused initialization vectors make it crackable in minutes with tools like aircrack-ng regardless of password strength -- WEP should never appear in any network built after the mid-2000s, and its presence today is itself a critical finding in a wireless assessment.
--> **WPA (Wi-Fi Protected Access)** -- a stopgap fix for WEP's flaws (introduced TKIP encryption) designed to run on the same hardware as WEP while a proper replacement was finalized -- also now considered broken/deprecated.
--> **WPA2** -- introduced AES-based CCMP encryption, was the standard for over a decade, and is what the 4-way-handshake capture/crack techniques in the Ethical Hacking wireless file target specifically.
--> **WPA3** -- the current standard, replacing WPA2's Pre-Shared Key exchange with SAE (Simultaneous Authentication of Equals, sometimes called "Dragonfly") -- this specifically defeats the offline dictionary/brute-force attack against a captured handshake that works against WPA2-PSK, since each authentication attempt requires interaction with the network rather than just a captured static handshake to crack offline. WPA3 also mandates PMF (Protected Management Frames), which closes off the deauthentication-attack technique (covered elsewhere in this track) that WPA2 networks are commonly vulnerable to.
--> **WPS (Wi-Fi Protected Setup)** -- a convenience feature (push-button or 8-digit PIN pairing) layered on top of WPA/WPA2, NOT a security protocol itself -- its 8-digit PIN is checked in two separate 4-digit halves by the access point, which cuts the effective brute-force search space enormously. This flaw (exploited by tools like Reaver) is why WPS should be disabled on any network regardless of which WPA version is otherwise in use.
--> **EAP (Extensible Authentication Protocol)** -- a FRAMEWORK for authentication methods, not a single protocol -- used in enterprise Wi-Fi (WPA2/WPA3-Enterprise) and other 802.1X network-access-control scenarios, where each user authenticates with their own credentials against a RADIUS server (covered in this track's authentication methodologies content) instead of everyone sharing one pre-shared key.
--> **PEAP (Protected EAP)** -- the most common EAP variant in practice -- wraps the actual authentication exchange inside a TLS tunnel (similar in spirit to LDAPS wrapping LDAP above), so credentials aren't exposed even though the inner authentication method itself might otherwise be weaker. This TLS wrapping is what lets an enterprise Wi-Fi network safely use simple username/password authentication for each employee instead of requiring every device to have its own client certificate.
